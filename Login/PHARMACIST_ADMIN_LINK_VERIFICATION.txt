PART 1: END-TO-END COMMUNICATION FLOW
================================================================================

REQUEST CREATION (Pharmacist → Admin):
─────────────────────────────────────

1. Pharmacist identifies low-stock medicine
   Location: Pharmacist Portal, Medicines Grid
   Trigger: RED "Low Stock" badge on medicine ≤10 units
   
2. Pharmacist clicks "Request Restock" button
   Action: Opens modal with medicine details
   Data Sent: medicine_id, medicine_name, current_quantity
   
3. Pharmacist fills in request details:
   - Request Quantity: How many units to restock
   - Reason: Why stock is low
   Action: Clicks "Submit Request"
   
4. System processes request:
   Endpoint: POST /api/restock-request
   Body: {
       actor_id: pharmacist_id,
       medicine_id: id,
       medicine_name: "Name",
       requested_quantity: 100,
       reason: "Low stock"
   }
   
5. Database records request:
   Table: restock_requests
   Status: 'pending'
   Data: Request ID, medicine, quantity, pharmacist_id, timestamp
   
6. Admin Portal immediately sees new request:
   Endpoint: GET /api/admin/restock-requests?status=pending
   Display: Request appears in "Restock Requests" section
   Badge: "⏳ Pending" (yellow)
   

APPROVAL FLOW (Admin → Pharmacist → Auto-Update):
──────────────────────────────────────────────────

1. Admin sees pending request in Admin Portal
   Location: Admin Portal, Restock Requests Tab
   Shows: Medicine, Pharmacist, Quantity, Reason
   Action: Reviews request details
   
2. Admin clicks "Approve & Add to Stock"
   Modal: Opens with optional notes field
   Admin enters: Approval notes (optional)
   Action: Clicks "Confirm"
   
3. System processes approval:
   Endpoint: PUT /api/admin/restock-request/{id}/approve
   Body: {
       actor_id: admin_id,
       admin_notes: "Approved - stock allocated"
   }
   
4. Backend auto-updates:
   a) Updates request status:
      UPDATE restock_requests SET status='approved'
   
   b) Updates medicine stock:
      UPDATE medicines SET quantity = quantity + 100
   
   c) Records timestamps:
      approved_at = NOW()
      approved_by = admin_id
   
5. Response returns updated quantities:
   {
       "message": "Restock request approved and inventory updated",
       "old_quantity": 5,
       "new_quantity": 105,
       "added_quantity": 100,
       "medicine_name": "Paracetamol 500mg"
   }
   
6. Pharmacist sees updates:
   a) In Inventory:
      Endpoint: GET /api/pharmacist/inventory
      Paracetamol: 5 → 105 units (GREEN "OK" badge)
   
   b) In Request Status:
      Endpoint: GET /api/pharmacist/restock-requests
      Status: PENDING → APPROVED
      Badge: ✓ Green with approval date
      

REJECTION FLOW (Admin → Pharmacist + Feedback):
───────────────────────────────────────────────

1. Admin sees pending request
   Decision: Request cannot be fulfilled (supplier issue, budget, etc)
   Action: Clicks "Reject" button
   
2. Admin provides rejection reason:
   Modal: Opens reason text field
   Input: Enters reason, e.g., "Supplier out of stock - will retry next week"
   Action: Clicks "Confirm Rejection"
   
3. System processes rejection:
   Endpoint: PUT /api/admin/restock-request/{id}/reject
   Body: {
       actor_id: admin_id,
       rejection_reason: "Supplier out of stock - will retry next week"
   }
   
4. Database records rejection:
   UPDATE restock_requests SET
       status='rejected',
       admin_notes='Supplier out of stock...',
       approved_at=NOW(),
       approved_by=admin_id
   
5. Response:
   {
       "message": "Restock request rejected",
       "reason": "Supplier out of stock - will retry next week"
   }
   
6. Pharmacist sees rejection with feedback:
   a) In My Restock Requests:
      Status: PENDING → REJECTED
      Badge: ✗ Red "REJECTED" status
   
   b) Feedback visible:
      "Admin Reason: Supplier out of stock - will retry next week"
      Pharmacist can read admin's explanation
   
7. Pharmacist can resubmit:
   After issue resolved, resubmit request
   Links back to same medicine
   Creates new separate request record

PART 4: DATA INTEGRITY & CONSISTENCY
================================================================================

FOREIGN KEY RELATIONSHIPS:

restock_requests table:
├── requested_by → login.id (Pharmacist who requested)
├── medicine_id → medicines.id (Medicine being requested)
└── approved_by → login.id (Admin who approved/rejected)

medicines table:
└── No direct link to restock_requests

TRANSACTION SAFETY:

When admin approves request:
1. BEGIN TRANSACTION
2. Update restock_requests status='approved'
3. Update medicines quantity
4. COMMIT (both changes atomic)
5. If error, both changes rolled back
6. No partial updates possible

UNIQUE CONSTRAINTS:

✓ Each request has unique ID (auto-increment)
✓ Email must be unique (no duplicate logins)
✓ Role must be valid ENUM value
✓ Timestamps auto-managed by database

STATUS VALIDATION:

✓ Request status must be: 'pending', 'approved', or 'rejected'
✓ Only one status per request
✓ Cannot change status twice (prevents admin confusion)
✓ Approval/rejection creates audit trail
